# 设计说明

## 阶段一：协议与并发

### 1. 协议选择

我选择“固定 8 字节头部 + JSON 负载”。

每个数据包的结构是：

```text
MAGIC(2) + VERSION(1) + TYPE(1) + LENGTH(4) + PAYLOAD
```

其中：

- `MAGIC` 固定为 `CL`；
- `VERSION` 当前固定为 `1`；
- `TYPE` 表示消息类型；
- `LENGTH` 表示 JSON 负载长度，使用网络大端序；
- `PAYLOAD` 是 UTF-8 编码的 JSON。

选择这个方案的原因：

1. 接收方可以先读取固定 8 字节头部；
2. 根据 `LENGTH` 可以准确判断一条消息是否收完；
3. JSON 容易调试，也适合登录、在线列表和聊天消息；
4. `TYPE` 字段方便以后增加新的消息类型；
5. `MAGIC` 和 `VERSION` 可以发现明显的错误数据。

代价：

1. 每条消息固定多 8 字节头部；
2. JSON 编码和解析比二进制格式更耗时；
3. 后续传文件时，如果继续使用 JSON 保存二进制内容，需要 Base64 编码，会增大体积。

当前阶段以正确性和易调试为主，因此接受这些代价。

---

### 2. 消息边界处理

TCP 是字节流，不保留消息边界，因此不能认为一次 `recv()` 就是一条消息。

接收流程固定为：

1. 使用 `recv_all()` 完整读取 8 字节头部；
2. 使用 `decode_header()` 检查魔数、版本和长度；
3. 根据头部中的 `LENGTH` 分配接收缓冲区；
4. 再使用 `recv_all()` 完整读取 JSON 负载；
5. 将类型和负载组合成一个 `Frame`。

因此：

- 一条消息分多次到达时可以正确还原；
- 多条消息粘在一起时，可以通过每条消息头部的长度正确拆分。

发送流程使用 `send_all()`：

1. 检查 `send()` 实际发送了多少字节；
2. 如果没有发送完，就从剩余位置继续发送；
3. 如果遇到 `EINTR`，就重试；
4. 使用 `MSG_NOSIGNAL` 防止向已关闭连接写入时进程被 `SIGPIPE` 终止。

---

### 3. 两层大小上限

协议层上限：

```text
4 MiB
```

它用于保护服务端内存。接收方在解析头部后、读取负载前检查 `LENGTH`。如果超过 4 MiB，不会分配对应大小的缓冲区。

业务层上限：

```text
1 MiB
```

它用于限制单条聊天消息中 `content` 字段的大小。即使整个 JSON 没有超过 4 MiB，只要聊天内容超过 1 MiB，服务端也会返回：

```text
MESSAGE_TOO_LARGE
```

这两个上限解决的问题不同：

- 协议层上限防止内存攻击；
- 业务层上限规定聊天功能允许的消息大小。

---

### 4. 异常输入处理

服务端处理以下异常：

| 异常 | 处理方式 |
|---|---|
| 魔数不是 `CL` | 返回 `PROTOCOL_ERROR` 并关闭连接 |
| 版本不是 `1` | 返回 `PROTOCOL_ERROR` 并关闭连接 |
| `LENGTH` 超过 4 MiB | 返回 `PROTOCOL_ERROR` 并关闭连接 |
| JSON 无法解析 | 返回 `BAD_REQUEST` |
| 必填字段缺失或类型错误 | 返回 `BAD_REQUEST` |
| 未登录就发送请求 | 返回 `NOT_LOGGED_IN` |
| 已登录后收到未知类型 | 返回 `UNKNOWN_TYPE` |
| 私聊目标不存在 | 返回 `USER_NOT_FOUND` |
| 聊天内容超过 1 MiB | 返回 `MESSAGE_TOO_LARGE` |

协议层错误通常表示数据包边界已经无法信任，因此发送错误后关闭连接。

业务层错误只表示当前请求无法处理，连接可以继续使用。

---

### 5. 并发模型

服务端使用“一连接一线程”：

1. 主线程负责 `accept()` 新连接；
2. 每个新连接创建一个 `std::thread`；
3. 每个连接线程循环读取和处理自己的客户端。

选择这个模型的原因：

1. 实现和理解都比较直接；
2. 一个客户端阻塞在 `recv()` 时，不影响其他客户端；
3. 阶段一的连接数量较少，不需要一开始就使用 `epoll`。

代价：

1. 每个连接都需要一个线程；
2. 连接数很大时会有较高的内存和调度成本；
3. 共享数据必须通过锁保护。

---

### 6. 在线用户表

服务端使用 `UserTable` 保存在线用户。

内部有两张表：

```text
username → ClientConnection
socket fd → username
```

第一张表用于私聊时根据用户名查找客户端。

第二张表用于连接断开时根据 socket 查找并删除用户名。

两张表由同一把互斥锁保护。每次更新会同时更新两张表，避免出现：

- 用户名存在但找不到连接；
- 连接存在但找不到用户名。

查询在线列表时，先在锁内复制结果，然后立刻释放锁。网络发送不持有用户表锁，以降低死锁风险。

---

### 7. 发送锁

多个线程可能同时给同一个客户端发送消息。

例如：

- 一个用户给 `bob` 发私聊；
- 另一个用户同时群发消息给所有人。

如果两个线程同时写 `bob` 的 socket，两个数据包可能交错。

因此每个 `ClientConnection` 都有一个：

```cpp
std::mutex send_mutex;
```

所有发送都通过统一函数：

```cpp
send_frame_to_client()
```

发送前先获取该客户端自己的发送锁，发送完成后自动释放。

这样保证：

- 同一个客户端的数据包不会交错；
- 不同客户端之间仍然可以并行发送。

---

### 8. 连接对象生命周期

客户端连接使用 `ClientConnection` 表示，其中包含：

- 由 `UniqueFd` 管理的 socket；
- 一个发送互斥锁。

服务端用户表保存：

```cpp
std::shared_ptr&lt;ClientConnection&gt;
```

这样做是为了避免下面的问题：

1. 群发线程刚从用户表中取出一个客户端；
2. 该客户端的连接线程同时退出；
3. 连接线程关闭 socket；
4. 群发线程继续使用已经关闭的 fd。

使用 `shared_ptr` 后，只要群发线程还持有 `ClientConnection`，连接对象和 socket 就不会提前销毁。

---

### 9. 掉线清理

客户端正常退出、执行 `/quit` 或被 `docker kill` 后，TCP 连接会关闭。

服务端连接线程中的 `recv()` 会返回 `0`，随后：

1. `recv_frame()` 返回 `false`；
2. 连接线程退出；
3. `LoginGuard` 的析构函数执行；
4. 从 `UserTable` 中删除该用户；
5. `UniqueFd` 自动关闭 socket。

这里使用 RAII 是为了保证：

- 正常返回时会清理；
- 异常导致线程退出时也会清理；
- 不需要在每个退出分支手工删除用户。

---

### 10. 心跳机制

当前没有实现心跳。

因此以下情况可以立刻发现：

- 客户端正常退出；
- 客户端进程被杀死；
- Docker 容器被 `docker kill`。

以下情况不一定能立刻发现：

- 客户端被 `docker pause`；
- 客户端收到 `SIGSTOP`；
- 网络断开但没有正常关闭 TCP 连接。

原因是这些情况下服务端不会立刻收到 TCP FIN，`recv()` 可能继续阻塞。

后续可以增加心跳：

1. 客户端每 5 秒发送一次 `PING`；
2. 服务端记录每个连接的最后活跃时间；
3. 服务端定期检查；
4. 超过 20 秒没有收到数据就关闭连接并删除用户。

---

### 11. 编码和资源管理

文本统一使用 UTF-8。

`std::string` 在这里用作字节缓冲区，可以保存包含任意字节的数据，但不使用 `strlen()` 等 C 字符串函数处理它。

资源管理方式：

- socket 由 `UniqueFd` 管理；
- 锁由 `std::lock_guard` 管理；
- 在线用户清理由 `LoginGuard` 管理；
- 容器和字符串自动管理内存。
