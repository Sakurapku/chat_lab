# 聊天协议说明

## 1. 协议目标

本项目使用 TCP 在客户端和服务端之间传输消息。

TCP 是面向字节流的协议，不保留应用层消息边界。一次 `send()` 发送的数据可能被拆成多次到达，多次 `send()` 发送的数据也可能被一次 `recv()` 收到。因此，通信双方必须通过自定义协议判断一条完整消息的起止位置。

本协议采用：

```text
固定 8 字节头部 + 可变长度 JSON 负载
```

协议主要解决以下问题：

1. 判断一条完整消息到哪里结束；
2. 区分不同类型的消息；
3. 防止超长消息导致服务端分配过多内存；
4. 发现明显的协议错误；
5. 为后续扩展新的消息类型保留空间。

---

## 2. 数据包结构

每个数据包由头部和负载组成：

```text
┌────────┬─────────┬──────┬────────────┬─────────────────────┐
│ MAGIC  │ VERSION │ TYPE │ LENGTH     │ PAYLOAD             │
│ 2 字节 │ 1 字节  │ 1字节│ 4 字节大端 │ LENGTH 字节的 JSON  │
└────────┴─────────┴──────┴────────────┴─────────────────────┘
```

### 2.1 字段说明

| 字段 | 大小 | 类型 | 说明 |
|---|---:|---|---|
| `MAGIC` | 2 字节 | 字节 | 固定为 ASCII 字符 `CL`，用于识别本协议 |
| `VERSION` | 1 字节 | 无符号整数 | 协议版本，当前固定为 `1` |
| `TYPE` | 1 字节 | 无符号整数 | 消息类型 |
| `LENGTH` | 4 字节 | 无符号整数 | JSON 负载的字节长度，使用网络大端序 |
| `PAYLOAD` | 可变 | UTF-8 JSON | 具体消息内容 |

### 2.2 长度计算规则

`LENGTH` 只表示 JSON 负载的长度，不包含前面的 8 字节头部。

例如 JSON 内容有 100 字节，则：

```text
LENGTH = 100
整个数据包长度 = 8 + 100 = 108 字节
```

### 2.3 字节序

`LENGTH` 是 4 字节无符号整数，传输时使用网络大端序。

发送方：

1. 先计算 JSON 的实际字节数；
2. 将长度从本机字节序转换为网络大端序；
3. 再发送头部和 JSON。

接收方：

1. 先读取 8 字节头部；
2. 将 `LENGTH` 从网络大端序转换回本机字节序；
3. 再按照该长度读取 JSON。

C/C++ 中可以使用：

- `htonl()`：将本机字节序转换为网络大端序；
- `ntohl()`：将网络大端序转换为本机字节序。

## 3. 消息类型

消息类型使用 `TYPE` 字段表示。

### 3.1 客户端发送给服务端

| 数值 | 名称 | 说明 |
|---:|---|---|
| `1` | `LOGIN_REQ` | 登录请求 |
| `2` | `LIST_USERS_REQ` | 请求在线用户列表 |
| `3` | `SEND_CHAT_REQ` | 发送聊天消息 |

### 3.2 服务端发送给客户端

| 数值 | 名称 | 说明 |
|---:|---|---|
| `101` | `LOGIN_RESP` | 登录结果 |
| `102` | `USER_LIST_RESP` | 在线用户列表 |
| `103` | `CHAT_MSG` | 服务端转发的聊天消息 |
| `104` | `ERROR_MSG` | 错误消息 |

以后新增消息类型时，只增加新的编号和对应 JSON 格式，不修改已有编号的含义。

---

## 4. JSON 消息格式

所有 JSON 文本统一使用 UTF-8 编码。

### 4.1 登录请求 `LOGIN_REQ`

客户端连接服务端后，首先发送登录请求：

```json
{
  "username": "alice"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `username` | string | 是 | 用户名 |

用户名要求：

1. 必须是字符串；
2. 去除首尾空白后不能为空；
3. 不能包含换行符；
4. 最长为 32 字节；
5. 同一时刻不能重复在线。

---

### 4.2 登录响应 `LOGIN_RESP`

登录成功：

```json
{
  "ok": true,
  "message": "login success"
}
```

登录失败：

```json
{
  "ok": false,
  "message": "username already exists"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `ok` | boolean | 是 | 登录是否成功 |
| `message` | string | 是 | 人类可读的登录结果 |

---

### 4.3 请求在线用户列表 `LIST_USERS_REQ`

客户端发送：

```json
{}
```

当前不需要额外字段，因此负载为空 JSON 对象。

---

### 4.4 在线用户列表响应 `USER_LIST_RESP`

服务端返回：

```json
{
  "users": ["alice", "bob"]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `users` | array | 是 | 当前在线用户名列表 |

如果没有其他用户在线，也应该返回空数组：

```json
{
  "users": []
}
```

---

### 4.5 发送聊天消息 `SEND_CHAT_REQ`

#### 群发消息

客户端向所有在线用户发送消息时，`to` 固定为 `"*"`：

```json
{
  "to": "*",
  "content": "大家好"
}
```

#### 私聊消息

客户端向指定用户发送消息时，`to` 是目标用户名：

```json
{
  "to": "bob",
  "content": "你好"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `to` | string | 是 | `"*"` 表示群发，其他值表示目标用户名 |
| `content` | string | 是 | 聊天内容 |

---

### 4.6 接收聊天消息 `CHAT_MSG`

服务端将聊天消息转发给接收者。

私聊消息：

```json
{
  "from": "alice",
  "to": "bob",
  "content": "你好"
}
```

群发消息：

```json
{
  "from": "alice",
  "to": "*",
  "content": "大家好"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `from` | string | 是 | 发送者用户名 |
| `to` | string | 是 | `"*"` 表示群发，其他值表示目标用户名 |
| `content` | string | 是 | 聊天内容 |

---

### 4.7 错误消息 `ERROR_MSG`

服务端发现请求无法正常处理时，向发送方返回：

```json
{
  "code": "USER_NOT_FOUND",
  "message": "user bob is not online"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `code` | string | 是 | 机器可识别的错误码 |
| `message` | string | 是 | 人类可读的错误说明 |

当前定义的错误码如下：

| 错误码 | 含义 |
|---|---|
| `PROTOCOL_ERROR` | 魔数、版本、长度等协议字段不合法 |
| `BAD_REQUEST` | JSON 格式错误或必填字段不合法 |
| `UNKNOWN_TYPE` | 消息类型不认识 |
| `NOT_LOGGED_IN` | 客户端尚未登录就发送其他请求 |
| `USER_NOT_FOUND` | 私聊目标不存在或不在线 |
| `MESSAGE_TOO_LARGE` | 聊天内容超过业务层大小上限 |

---

## 5. 大小限制

### 5.1 协议层上限

单个 JSON 负载最大为：

```text
4 MiB = 4 × 1024 × 1024 字节
```

协议层上限用于保护服务端内存。接收方在读取 JSON 内容之前，必须先检查头部中的 `LENGTH`。

如果 `LENGTH` 超过 4 MiB：

1. 不分配对应大小的缓冲区；
2. 返回 `PROTOCOL_ERROR`，或直接断开连接；
3. 记录错误日志。

### 5.2 业务层上限

单条聊天消息中 `content` 字段最大为：

```text
1 MiB = 1024 × 1024 字节
```

业务层上限是聊天功能自身的规则。即使整个 JSON 没有超过协议层的 4 MiB，只要 `content` 超过 1 MiB，也必须拒绝该请求。

服务端应向发送方返回：

```json
{
  "code": "MESSAGE_TOO_LARGE",
  "message": "message content exceeds 1 MiB"
}
```

### 5.3 字节数与字符数

大小限制按照 UTF-8 编码后的字节数计算，不是按照字符个数计算。

例如，一个汉字在 UTF-8 中通常占 3 字节。程序必须检查字符串的 `size()`，而不是简单统计肉眼看到的字符数。

## 6. 登录流程

### 6.1 登录成功

1. 客户端建立 TCP 连接；
2. 客户端发送 `LOGIN_REQ`；
3. 服务端检查用户名是否合法；
4. 服务端检查用户名是否已经在线；
5. 检查通过后保存用户名和连接的对应关系；
6. 服务端返回登录成功的 `LOGIN_RESP`。

### 6.2 用户名重复

如果用户名已经在线，服务端返回：

```json
{
  "ok": false,
  "message": "username already exists"
}
```

随后服务端可以关闭连接。

### 6.3 未登录就发送其他请求

如果客户端没有先登录，就发送 `LIST_USERS_REQ` 或 `SEND_CHAT_REQ`，服务端返回：

```json
{
  "code": "NOT_LOGGED_IN",
  "message": "please login first"
}
```

如果客户端尚未登录，除 `LOGIN_REQ` 以外的消息会优先返回
`NOT_LOGGED_IN`；只有已经完成登录的连接收到未知类型时才返回
`UNKNOWN_TYPE`。
---

## 7. 在线列表流程

1. 客户端发送 `LIST_USERS_REQ`；
2. 服务端读取当前在线用户表；
3. 服务端生成用户名数组；
4. 服务端发送 `USER_LIST_RESP`。

服务端返回的在线列表必须与当前在线用户表一致。

如果客户端在查询前已经掉线，服务端应先清理该连接，再生成在线列表。

---

## 8. 聊天流程

### 8.1 群发流程

1. 客户端发送 `SEND_CHAT_REQ`；
2. 服务端检查发送者是否已登录；
3. 服务端检查 `to` 是否为 `"*"`；
4. 服务端检查 `content` 是否合法；
5. 服务端将 `CHAT_MSG` 发送给所有在线用户。

发送者自己也可以收到消息，方便确认消息已经成功到达服务端。

### 8.2 私聊流程

1. 客户端发送 `SEND_CHAT_REQ`；
2. 服务端检查发送者是否已登录；
3. 服务端检查目标用户名是否存在；
4. 服务端检查目标用户是否在线；
5. 如果目标在线，服务端将 `CHAT_MSG` 发送给目标用户；
6. 如果目标不存在或不在线，服务端向发送者返回 `USER_NOT_FOUND`。

私聊消息只有目标用户能够收到，其他在线用户不能收到。

---

## 9. 异常数据处理

### 9.1 MAGIC 不正确

如果头部前两个字节不是 `CL`：

1. 说明数据不符合本协议；
2. 不继续解析该数据包；
3. 返回 `PROTOCOL_ERROR` 或断开连接。

### 9.2 VERSION 不正确

当前协议版本为 `1`。

如果版本号不是 `1`：

1. 返回 `PROTOCOL_ERROR`；
2. 可以断开连接。

### 9.3 LENGTH 不合法

如果 `LENGTH` 超过协议层上限 4 MiB：

1. 不读取对应长度的数据；
2. 不分配对应大小的内存；
3. 返回 `PROTOCOL_ERROR` 或断开连接。

### 9.4 JSON 解析失败

如果负载不是合法 JSON：

1. 服务端不能崩溃；
2. 返回：

```json
{
  "code": "BAD_REQUEST",
  "message": "invalid JSON payload"
}
```

### 9.5 JSON 字段不完整

如果 JSON 可以解析，但缺少必填字段，或字段类型不正确，返回：

```json
{
  "code": "BAD_REQUEST",
  "message": "missing or invalid field"
}
```

### 9.6 消息类型不认识

如果 `TYPE` 不在当前协议定义范围内，返回：

```json
{
  "code": "UNKNOWN_TYPE",
  "message": "unknown message type"
}
```

### 9.7 私聊目标不在线

如果目标用户不存在或已经掉线，返回：

```json
{
  "code": "USER_NOT_FOUND",
  "message": "target user is not online"
}
```

## 10. 连接断开处理

### 10.1 客户端正常退出或被终止

客户端正常关闭连接或被 `docker kill` 后，服务端调用 `recv()` 会返回 `0`。

服务端应当：

1. 关闭对应 socket；
2. 从在线用户表中删除该用户；
3. 释放该连接占用的资源。

### 10.2 客户端暂时失去响应

客户端被 `docker pause`、`SIGSTOP` 或网络异常中断时，TCP 连接可能仍然处于已连接状态，服务端不能立刻通过 `recv()` 返回 `0` 发现问题。

该问题后续可以通过心跳机制解决：

1. 客户端定期发送心跳；
2. 服务端记录每个连接的最后活跃时间；
3. 超过超时时间仍没有收到数据，则关闭连接并清理在线状态。

心跳属于选做功能。如果实现，心跳间隔和超时时间需要写入 `docs/design.md`。

## 11. 数据收发要求

### 11.1 接收数据

不能认为调用一次 `recv()` 就一定会收到一条完整消息。

接收方需要：

1. 先完整读取 8 字节头部；
2. 检查 `MAGIC`、`VERSION` 和 `LENGTH`；
3. 再根据 `LENGTH` 完整读取 JSON；
4. 将多个字段组合成一条完整消息。

一条消息可能分多次到达，接收方必须继续读取，直到收够指定字节数。

### 11.2 发送数据

不能认为调用一次 `send()` 就一定会把所有数据发送出去。

发送方必须检查 `send()` 的返回值：

- 如果只发送了一部分，就从剩余位置继续发送；
- 如果被信号打断，就重试；
- 如果连接已经断开，就停止发送并处理错误。

### 11.3 多线程写入

如果多个线程可能同时向同一个 socket 写入数据，必须使用发送锁。

否则两个线程的数据可能交错，导致接收方读到损坏的数据包。

---

## 12. 当前协议的限制

当前协议主要用于阶段一的命令行聊天，因此有以下限制：

1. 使用 JSON 作为负载，传二进制文件时需要额外编码；
2. 暂时不加密，不能防止网络中的窃听；
3. 用户名没有密码验证；
4. 暂时不支持历史消息；
5. 暂时不支持离线消息；
6. 心跳机制属于选做功能。

这些限制将在后续阶段逐步改进。

---

## 13. 示例数据包

假设客户端发送登录请求：

```json
{"username":"alice"}
```

该 JSON 的 UTF-8 长度为 20 字节，则头部字段为：

| 字段 | 内容 |
|---|---|
| `MAGIC` | `CL` |
| `VERSION` | `1` |
| `TYPE` | `1`，表示 `LOGIN_REQ` |
| `LENGTH` | `20`，使用网络大端序 |
| `PAYLOAD` | `{"username":"alice"}` |

接收方收到数据后，应当：

1. 检查前两个字节是否为 `CL`；
2. 检查版本是否为 `1`；
3. 读取消息类型 `1`；
4. 读取负载长度 `20`；
5. 继续读取 20 字节 JSON；
6. 将消息解析为登录请求。
